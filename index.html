1One Certificate at a Time

This is a deliberately modest utility. Given one X.509 certificate, the program records its observations in a log: it examines the validity dates, inspects which signature algorithm was used, looks at three extensions, and tries the signature against the public key belonging to that same certificate. It writes no file, alters nothing, and validates no chain.

The Signature Test Is Self Signed Only. Trying a signature against the certificate's own key is a self-signed consistency experiment. It yields a genuine verdict solely when the certificate is self-signed. A certificate from a certificate authority was signed with the issuer's key, so this experiment reports failure even on a perfectly healthy authority-issued certificate. A real verdict for such a certificate would need the issuer certificate's public key, and this utility accepts no issuer certificate argument.

2Before the Walk: Requirements and Launch

Running the tool presupposes Python 3 together with the cryptography package at version 41.0.7 or newer, the floor recorded in the requirements file. Because main.py imports that package at the head of the file, a machine lacking it halts at the imports even when only help output was wanted, and no help output appears.

Acquisition, exactly as published:

git clone https://github.com/ShadowGuard-AI/crypto-x509-analyzer
cd crypto-x509-analyzer
pip install -r requirements.txt

The clone line is accurate as it stands: it names ShadowGuard-AI with its hyphen and carries no .git ending. The only invocation shape that works is python3 main.py <certificate path>, run from inside the cloned directory, with -v or --verbose appended for debug level logging. No executable and no installable package bears the repository name.

3Arguments, in Parser Order

  • certificate_path: positional, obligatory, a PEM encoded certificate.
  • -v, --verbose: raises logging to DEBUG level.
  • -h: help, provided by argparse.

4Loading, the Calendar, and Three Weak OIDs Named

The program reads the nominated file as uninterpreted bytes. A file that cannot be found logs an error; a read failure logs an error; either way the run finishes with exit code 1. The bytes are then loaded strictly as PEM. DER input is turned away with a message requesting PEM format, and the run also finishes at exit 1.

Calendar examination follows the code's own order: a warning when the beginning of validity falls after the end, a warning when the beginning still lies in the future, and a warning when the end has already gone by. The latter two comparisons rely on the clock of the machine running the tool, so an incorrectly set clock can make a healthy certificate appear premature or overdue.

The signature algorithm object identifier is logged. Exactly three identifiers attract a weak warning: RSA with MD5, RSA with SHA1, and DSA with SHA1. No other identifier attracts that warning. ECDSA with SHA1 and RSA with MD2 pass without it, and an absence of warning means only that none of the three appeared.

5Three Extensions, Then the Signature

Key Usage is logged, and its absence provokes a warning describing the absence as a possible security risk. Basic Constraints is logged, with a true CA value reported as a CA certificate and a false value as an end entity certificate; a missing Basic Constraints is merely logged as not found, with no warning. Subject Alternative Name is logged, and if missing, likewise logged as not found without a warning. No other extension is opened, and the critical marker on any extension is never examined.

Signature testing branches by key family: RSA keys with PKCS1v15 padding and the certificate hash, ECDSA keys with ECDSA and that hash, Ed25519 keys with no hash argument, DSA keys with the hash handed over directly. An unsupported key family ends as a logged error inside the experiment, while the run still reports success. Success brings a log line clarifying that neither issuer checking nor chain checking has taken place. Key length receives no examination for any key family, and chain validation, revocation checking, and hostname checking appear nowhere in the code.

6The Second CA Pass, and the Duplicated Subject

After the signature attempt, the program fetches Key Usage and Basic Constraints a second time and complains when a CA certificate has a Key Usage that omits keyCertSign. In this second pass a missing extension passes without comment, even though the earlier pass logged that same absence, so the two passes can give differing impressions of one certificate. The run winds up by logging issuer and subject, and subject was already logged when the run began, so it shows up twice in total.

7Findings Never Change the Exit, and the Licensing Picture

Everything discovered lives only in the log, and no discovery alters the exit code. An expired certificate, a suspect algorithm, and an unsuccessful signature experiment each still finish at exit 0. Exit 1 carries a single meaning: the certificate file could not be read, or could not be parsed.

The Record as Published

The live README, preserved verbatim:

![Banner](banner.png)

# crypto-x509-analyzer
A tool to parse and analyze X.509 certificates, highlighting potential vulnerabilities such as weak signature algorithms, expired dates, or missing critical extensions. - Focused on Basic cryptographic operations

What the signature line means: the tool checks the certificate signature against the certificate's own public key. That is a self-signed consistency check, and it is a real signature verdict only for a self-signed certificate. A CA issued certificate was signed with the issuer's key, so this check fails on sound CA issued certificates; a real signature verdict for one needs the issuer certificate's public key, and this tool does not take an issuer certificate argument. Findings are reported in the log only: no finding, including an expired certificate or a weak signature algorithm, changes the exit code. The run exits 1 only when the certificate file cannot be read or parsed.

## Install
`git clone https://github.com/ShadowGuard-AI/crypto-x509-analyzer`
Then install the one dependency from the cloned directory: `pip install -r requirements.txt`

## Usage
`python3 main.py [-h] [-v] certificate_path`, run from the cloned directory. There is no executable or package by the repo name. Input must be a PEM encoded certificate; DER input is not accepted and fails with an error asking for PEM format.

## Parameters
- `certificate_path`: Path to the X.509 certificate file (PEM format). Required.
- `-h`: Show help message and exit
- `-v`: Enable verbose logging (DEBUG level).
